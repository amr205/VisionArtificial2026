02 / 13
Introducción

¿Por qué necesitamos DVC en investigación?

❌ Sin DVC

  • data_v3_final2.csv — versiones manuales
  • Notebooks con resultados sobreescritos
  • No sabes qué parámetros generaron cada gráfica
  • Imposible reproducir el paper 6 meses después
  • Colaboradores obtienen resultados distintos

✅ Con DVC

  • Datos trackeados por hash, no duplicados
  • Cada experimento guarda métricas, modelo y plots
  • dvc repro re-corre exactamente lo necesario
  • dvc exp show compara todos los runs
  • Reproducible en cualquier máquina con dvc pull

🔑 Principio clave

DVC no reemplaza a Git — lo extiende. Git versiona código; DVC versiona datos, modelos y métricas con el mismo flujo de trabajo.

03 / 13
Conceptos clave

¿Qué es DVC?

DVC se integra con Git. Mientras Git versiona el código, DVC versiona los datos, modelos y métricas.

📄 Archivos .dvc

Punteros ligeros que reemplazan archivos grandes en Git. El archivo real vive en caché; el .dvc con su hash MD5 sí va a Git.

⚙️ dvc.yaml

Define el DAG: etapas, dependencias, outputs, métricas y parámetros. DVC construye el grafo y sabe qué re-correr automáticamente.

🎛️ params.yaml

Todos los hiperparámetros en un solo lugar. Si un valor cambia, la etapa que lo consume se invalida automáticamente.

04 / 13
Gestión de datos

Versionar datos con dvc add

Los datos van a un remote storage. Git solo guarda el .dvc con el hash.

dvc add data/raw/turismo.csv
git add data/raw/turismo.csv.dvc .gitignore
git commit -m "data: add raw v1"
dvc remote add -d myremote gdrive://<id>
dvc push  # sube datos al remoto
dvc pull  # colaborador descarga

¿Por qué no en Git?

Git no escala con archivos >50 MB. DVC guarda el hash en Git y el binario en el remoto. Mismo hash = cero espacio extra.

Remotos soportados

Google DriveS3GCS Azure BlobSSHlocal

Pipeline

Definir un pipeline en dvc.yaml

data/raw/
→
clean
→
features
→
train
→
evaluate
→
interpret
stages:
  train:
    cmd: python src/train.py
    deps: [src/train.py,
           data/features/features.csv,
           params.yaml]
    params: [model, train]
    outs:
      - models/model.json:
          cache: false
    metrics:
      - metrics/metrics.json:
          cache: false

¿Qué monitorea DVC?

  • deps: hash de archivos de entrada
  • params: valores en params.yaml
  • cmd: el comando mismo

Si alguno cambia → etapa y descendientes se re-corren.

💡 cache: false

El archivo se guarda en Git (legible en historial), no solo en caché DVC. Ideal para métricas, plots y CSVs pequeños.

06 / 13
Pipeline

Las etapas del pipeline de investigación

1 · Limpieza (clean.py)

Lee raw CSV, imputa nulos, normaliza fechas. Output con cache: false para verlo en Git.

2 · Features (features.py)

Rezagos, medias móviles, dummies de trimestre. Parámetros como lags vienen de params.yaml.

3 · Entrenamiento (train.py)

Split cronológico, ajusta modelo, guarda model.json y metadatos del split.

4 · Evaluación (evaluate.py)

MAE, RMSE, MAPE, R² → metrics.json. Plot del pronóstico → plots/.

5 · Interpretación (interpret.py)

SHAP bar chart + descomposición STL de tendencia y estacionalidad.

📂 Estructura de outputs

models/ · metrics/ · plots/ · data/processed/ · data/features/

07 / 13
params.yaml

Centralizar hiperparámetros en params.yaml

# params.yaml
target: consumo_turistico

features:
  lags: [1, 2, 3, 4]
  rolling_windows: [2, 4]
  add_quarter_dummies: true

model:
  type: xgboost
  xgboost:
    n_estimators: 100
    max_depth: 3
    learning_rate: 0.1
    subsample: 0.8

train:
  test_size: 0.2

¿Por qué importa?

Un cambio invalida exactamente las etapas afectadas. Nada más, nada menos.

Leer desde Python

import yaml
with open("params.yaml") as f:
    p = yaml.safe_load(f)
lags = p["features"]["lags"]

Cambiar desde CLI

dvc exp run \
  --set-param model.xgboost.max_depth=6
# no toca params.yaml directamente
08 / 13
Reproducibilidad

Correr y reproducir el pipeline

dvc repro
# solo corre etapas cambiadas

dvc repro --force
# fuerza re-ejecución de todo

dvc repro train
# etapa específica + descendientes

dvc dag
# visualiza el grafo ASCII

dvc status
# qué etapas están desactualizadas

dvc metrics show
# métricas del run actual

🔑 Cómo decide DVC qué re-correr

Hashea deps + params + código. Hash sin cambios → Stage cached. Hash cambiado → etapa y descendientes re-corren.

dvc repro es idempotente: seguro de correr siempre.

🔄 Flujo con Git

  • Cambia código o params
  • dvc repro → solo re-corre lo necesario
  • git add dvc.lock metrics/ plots/
  • git commit → snapshot completo
09 / 13
Experimentos

Experimentación con dvc exp run

Cada run crea un experimento nombrado que guarda params, métricas, modelo y plots — sin branches manuales.

dvc exp run --name baseline

dvc exp run \
  --set-param model.xgboost.max_depth=6 \
  --name depth6

dvc exp run \
  --set-param "features.lags=[1,2,4,8]" \
  --name lags_ext

dvc exp run \
  --set-param model.xgboost.n_estimators=300 \
  --set-param model.xgboost.max_depth=5 \
  --name n300_depth5

¿Qué se guarda en cada experimento?

  • Snapshot de params.yaml
  • JSON de métricas (MAE, RMSE, R²…)
  • Modelo entrenado
  • Plots generados
  • Hash del código y los datos
  • Timestamp del run

💡 Sin branches de Git

DVC guarda los experimentos en refs especiales de Git. No contamina tu historial de branches.

Model Registry

Agregar modelos sin tocar el pipeline

Interfaz BaseForecaster

Métodos: fit, predict, save, load, get_shap_explainer.

Agregar un modelo nuevo

  1. Crear src/models/mi_modelo.py
  2. Implementar BaseForecaster
  3. Registrar en __init__.py
  4. Agregar params en params.yaml
  5. Cambiar model.type y correr
# params.yaml
model:
  type: xgboost  # ← solo cambia esto
  xgboost:
    max_depth: 3
    n_estimators: 100
  random_forest:
    n_estimators: 200
    max_features: sqrt
  # lstm:
  #   hidden_size: 64
  #   epochs: 100

Comparar modelos

dvc exp run \
  --set-param model.type=random_forest \
  --name rf_model
dvc exp show --only-changed

Resumen

Flujo de trabajo completo

Setup (una vez)

git init && dvc init
dvc add data/raw/*.csv
dvc remote add -d remote <url>
git add . && git commit -m "init"

Reproducir

dvc repro
dvc metrics show && dvc dag

Experimentar

dvc exp run \
  --set-param model.xgboost.max_depth=6 \
  --name depth6
dvc exp show --csv > results.csv

Adoptar y committear

dvc exp apply depth6
git add . && git commit \
  -m "feat: adopt depth6"

git checkout <hash> + dvc checkout → reproducir cualquier resultado anterior, incluyendo datos y modelo.
