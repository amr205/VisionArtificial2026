Motivación

El problema de la reproducibilidad

❌ Flujo sin control

  • data_v3_final2.csv — versiones manuales
  • Notebooks sobreescritos sin historial
  • "¿Con qué parámetros entrené este modelo?"
  • Resultados distintos entre máquinas
  • Imposible comparar dos experimentos de la semana pasada

💬 Escenario real

Un revisor de tu paper pide reproducir la Tabla 3. Los datos cambiaron, no recuerdas los hiperparámetros exactos, y el modelo fue sobreescrito.

✅ Flujo con DVC

  • Datos versionados por hash criptográfico
  • Pipeline reproducible como código
  • Cada experimento: params + métricas + modelo + predicciones
  • dvc exp apply tabla3 → workspace restaurado
  • Compartir con dvc push/pull como Git

🔑 Principio clave

DVC extiende Git, no lo reemplaza. Git versiona código; DVC versiona datos y modelos con el mismo flujo de trabajo.

03 / 14
Conceptos clave

Los tres pilares de DVC

📄 Archivos .dvc

Puntero ligero que reemplaza el archivo grande en Git. Contiene el hash MD5 del contenido real.

outs:
- md5: a1b2c3...
  path: data/raw/data.csv

⚙️ dvc.yaml

Define el DAG del pipeline: etapas, dependencias, outputs, métricas y parámetros. DVC construye el grafo y sabe qué re-correr.

🎛️ params.yaml

Todos los hiperparámetros centralizados. Si un valor cambia, DVC invalida solo las etapas que dependen de él.

El flujo básico

git init + dvc init → dvc add data/ → scripts + dvc.yaml + params.yaml → dvc repro → dvc exp run → dvc exp show

04 / 14
Gestión de datos

Versionar datos con dvc add

Git guarda el .dvc (hash). Los datos reales van al remote storage.

dvc add data/raw/dataset.csv
git add data/raw/dataset.csv.dvc .gitignore
git commit -m "data: add raw dataset v1"

dvc remote add -d storage gdrive://<id>
dvc push   # sube datos al remoto

# Colaborador clona y descarga
git clone <repo> && dvc pull

Actualizar datos

Reemplaza el archivo → dvc add → nuevo hash → git commit. DVC conserva ambas versiones en caché (deduplicación automática).

¿Por qué no en Git?

  • Git no escala con archivos >50 MB
  • DVC usa deduplicación por hash: mismo dato = cero espacio extra
  • El .dvc es ligero y viaja en Git normalmente

Remotos soportados

Google DriveS3GCSAzure BlobSSHlocal

Pipeline

Definir un pipeline reproducible en dvc.yaml

data/raw/
→
clean
→
features
→
train
→
evaluate
stages:
  train:
    cmd: python src/train.py
    deps:
      - src/train.py
      - data/features/X_train.csv
      - params.yaml
    params: [model, train]
    outs:
      - models/model.pkl:
          cache: false
      - data/predictions/test_preds.csv:
          cache: false
    metrics:
      - metrics/metrics.json:
          cache: false
    plots:
      - plots/confusion_matrix.png:
          cache: false

¿Qué monitorea DVC por etapa?

  • deps: hash de scripts y datos de entrada
  • params: valores leídos de params.yaml
  • cmd: el comando mismo

Cualquier cambio → etapa + descendientes se re-corren.

💡 cache: false

El output sí va a Git. Úsalo para modelo, predicciones, métricas y plots — los artefactos que quieres comparar entre experimentos sin volver a correr nada.

06 / 14
Configuración

Centralizar hiperparámetros en params.yaml

# params.yaml
data:
  test_size: 0.2
  random_state: 42
  stratify: true

features:
  scaling: standard   # standard | minmax
  pca_components: null

model:
  type: random_forest # swappable
  random_forest:
    n_estimators: 100
    max_depth: 5
  logistic:
    C: 1.0
    max_iter: 200

evaluate:
  threshold: 0.5

Leer en Python

import yaml
with open("params.yaml") as f:
    p = yaml.safe_load(f)
n_est = p["model"]["random_forest"]["n_estimators"]

Por qué un solo archivo

  • DVC lo monitorea automáticamente
  • Fuente de verdad para todos los scripts
  • Cambiar sin editar: --set-param
  • El historial de Git muestra exactamente qué cambió
07 / 14
Reproducibilidad

dvc repro — ejecución inteligente del pipeline

dvc repro
# corre solo etapas desactualizadas

dvc repro --force
# fuerza re-ejecución de todo

dvc repro evaluate
# etapa específica + sus dependencias

dvc dag
# grafo ASCII del pipeline

dvc status
# qué etapas están desactualizadas

dvc metrics show
# métricas del workspace actual

dvc metrics diff HEAD~1
# comparar con commit anterior

🔑 Lógica de invalidación

DVC hashea deps + params + código de cada etapa y guarda el resultado en dvc.lock.

  • Hash igual → Stage cached, se salta
  • Hash distinto → re-ejecuta + propaga a descendientes

dvc repro es idempotente: siempre seguro de correr.

Flujo típico en investigación

  1. Edita un script o un param
  2. dvc repro → solo re-corre lo necesario
  3. git add dvc.lock metrics/ plots/
  4. git commit → snapshot reproducible
08 / 14
Experimentos

dvc exp run — experimentos nombrados

Cada run crea un snapshot completo: params, métricas, modelo, predicciones y plots. Sin branches manuales de Git.

# Baseline
dvc exp run --name baseline

# Cambiar hiperparámetro
dvc exp run \
  --set-param model.random_forest.max_depth=10 \
  --name depth10

# Cambiar tipo de modelo
dvc exp run \
  --set-param model.type=logistic \
  --name logistic_c1

# Varios params a la vez
dvc exp run \
  --set-param model.random_forest.n_estimators=300 \
  --set-param features.scaling=minmax \
  --name rf300_minmax

¿Qué se guarda por experimento?

  • Snapshot de params.yaml
  • metrics/metrics.json
  • models/model.pkl
  • data/predictions/test_preds.csv
  • Todos los plots generados
  • Hash del código y los datos usados

Sin contaminar Git

DVC guarda los experimentos en refs especiales (refs/exps/). Tu historial de branches permanece limpio.

Restaurar cualquier experimento

dvc exp apply <nombre> restaura el workspace completo: params, modelo, predicciones y plots.

Artefactos

Archivar artefactos localmente

El problema con nombres fijos

Cada dvc exp run sobreescribe model.pkl, test_preds.csv y metrics.json en el workspace. DVC los preserva internamente, pero acceder a ellos side-by-side requiere dvc exp apply por cada uno.

Solución: archive_experiment.py

Script que copia todos los artefactos del workspace a una carpeta nombrada.

python archive_experiment.py \
  --name depth10
# Crea experiments/depth10/ con:
# model.pkl, test_preds.csv,
# metrics.json, plots/,
# params_snapshot.yaml, metadata.json
experiments/ ← en .gitignore
  ├── baseline/
  │   ├── model.pkl
  │   ├── test_preds.csv
  │   ├── metrics.json
  │   ├── plots/
  │   ├── params_snapshot.yaml
  │   └── metadata.json
  └── depth10/
      ... misma estructura

¿Commit de experiments/?

No es necesario. La fuente de verdad es DVC (dvc exp apply restaura todo). Esta carpeta es caché local para comparación rápida. Para compartir con el equipo: dvc exp push.

Flujo completo

El flujo de trabajo en investigación

1 · Setup (una vez)

git init && dvc init
dvc add data/raw/
dvc remote add -d storage <url>
git add . && git commit -m "init"

2 · Desarrollar el pipeline

Scripts + dvc.yaml + params.yaml → dvc repro → git commit

3 · Experimentar

dvc exp run \
  --set-param model.rf.max_depth=10 \
  --name depth10
python archive_experiment.py \
  --name depth10

4 · Comparar

dvc exp show --csv > results.csv
# Analizar en Python / Jupyter

5 · Adoptar el mejor

dvc exp apply depth10
git add params.yaml dvc.lock metrics/ plots/
git commit -m "exp: adopt depth10"
dvc push

6 · Reproducir cualquier resultado

git checkout <hash>
dvc checkout  # o dvc exp apply <nombre>

Buenas prácticas

Diseño del pipeline para investigación

Model Registry pattern

Permite cambiar el algoritmo con un solo parámetro:

REGISTRY = {
  "random_forest": RFModel,
  "logistic": LogisticModel,
  "svm": SVMModel,
}
model = REGISTRY[p["model"]["type"]](p)

Separación de responsabilidades

  • clean.py — solo limpieza
  • features.py — solo feature engineering
  • train.py — solo entrenamiento
  • evaluate.py — solo métricas y plots

Cada script: lee disco → procesa → escribe disco.

Qué guardar siempre

  • modelo — para inference o comparación
  • predicciones en test — para análisis post-hoc
  • métricas JSON — para dvc exp show
  • plots — para paper y presentaciones
  • params snapshot — auditoría completa

Para modelos pesados (DL)

No archivar el modelo localmente. Usar dvc push después de cada run satisfactorio. El equipo lo descarga con dvc exp pull.

Colaboración

Trabajo en equipo con DVC

Compartir datos y modelos

dvc push   # subir al remoto compartido

# Colaborador clona y descarga
git clone <repo>
dvc pull

Compartir experimentos

dvc exp push origin depth10

dvc exp pull depth10
dvc exp apply depth10

Lo que sí va a Git

  • dvc.yaml, dvc.lock, params.yaml
  • metrics/metrics.json
  • plots/ (con cache: false)
  • Scripts en src/

Lo que NO va a Git

  • Datos crudos y procesados
  • Modelos (van al remoto de DVC)
  • experiments/ (en .gitignore)
  • .dvc/cache/

DagsHub como alternativa

Actúa como remoto de DVC + UI de MLflow. Cualquier colaborador ve los experimentos desde el navegador sin instalar nada.

Resumen

DVC en tu investigación: lo esencial

📦 Datos

  • dvc add para trackear
  • dvc push/pull para compartir
  • El .dvc va a Git; el dato al remoto
  • Deduplicación automática por hash

⚙️ Pipeline

  • Scripts independientes por etapa
  • dvc.yaml define el DAG
  • params.yaml centraliza params
  • dvc repro es idempotente

🔬 Experimentos

  • dvc exp run --name
  • archive_experiment.py para acceso local
  • dvc exp show --csv para comparar
  • dvc exp apply restaura todo

Regla de oro

Si alguien clona tu repo y corre dvc pull + dvc repro, debe obtener exactamente los mismos resultados. Si no es posible, algo falta en el pipeline.
